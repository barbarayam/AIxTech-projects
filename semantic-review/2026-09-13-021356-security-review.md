# Security review: Singapore weather dashboard

The app is a full-stack weather dashboard—Node/Express backend, React/Vite frontend, SQLite via Drizzle ORM—that stores Singapore coordinates and fetches live weather from the data.gov.sg APIs. The attack surface is narrow, but several gaps are worth addressing before exposing this beyond localhost. The logging endpoint accepts user-controlled content that reaches the structured log with minimal sanitisation, there is no CORS policy, the `frontmanPlugin` in the Vite config is a third-party plugin that phones home to `api.frontman.sh`, and `npm audit` reports 14 high-severity vulnerabilities in the dependency tree.

**Watch for:** The `frontmanPlugin` dependency (`@frontman-ai/vite`) sends data to an external host during the build/dev phase — confirm what it transmits and whether it belongs in CI. The missing CORS header means any origin can hit the API if it's ever reachable beyond 127.0.0.1. The `/api/logs` endpoint mirrors unsanitised user content into the log stream.

**Verdict**: NEEDS_CHANGES

---

## High-level view

Input validation for location coordinates is solid on the create path — `Number()` coercion, `isNaN` guards, and an explicit Singapore bounding box. The gap is at the path-parameter level: the GET and refresh routes coerce `locationId` with `Number()` but never check for `NaN`, so `/api/locations/abc` silently resolves to a not-found rather than the correct 422. The delete handler already has this guard; the others don't.

The `/api/logs` endpoint validates the `event` field with an allowlist regex but accepts the `metadata` object and the `page` field as arbitrary caller-supplied content logged verbatim into the structured log record. Any caller can inject keys that collide with log aggregation fields or plant false-positive alert patterns.

No CORS middleware is configured. The server binds to `127.0.0.1` in development, which limits current exposure, but the absence of an explicit policy means protection depends entirely on deployment topology — a reverse proxy adding permissive CORS headers, or any future middleware change, would open the API to cross-site requests with no server-side guardrail.

The `WEATHER_API_KEY` is loaded correctly from an environment variable and never appears in any response body. The `.gitignore` excludes `.env` and `.env.*`. The key is visible in pino-http output if `LOG_LEVEL=debug` is set, since `.env.example` places no constraint on that variable.

The `frontmanPlugin` (`@frontman-ai/vite: ^0.5.2`) connects to `api.frontman.sh` with `projectRoot` and `sourceRoot` pointing at the frontend directory, giving it access to the source tree at build/dev time. The bulk of the `npm audit` high-severity findings — `puppeteer-core`, `extract-zip`, `lighthouse`, `@sentry/node`, `brace-expansion` — are transitive through this plugin's dependency tree. The `vite 7.0.0–7.3.3` and `body-parser` vulnerabilities are independent of that chain and have fixes available via `npm audit fix`.

<summary>Issues (8)</summary>

1. **NaN locationId reaches the database** — `GET /api/locations/:locationId` and `POST /api/locations/:locationId/refresh` use `Number(request.params.locationId)` without an `isNaN` guard. A non-numeric ID silently queries the DB with `NaN` and returns 404 instead of 422. Add the same guard that the delete handler already has.

2. **Unvalidated `metadata` and `page` in `/api/logs`** — The `metadata` object and `page` string are taken from the request body and logged verbatim. An attacker can inject arbitrary key-value pairs into structured log entries, polluting aggregation pipelines or creating false alerts. Allowlist accepted `metadata` fields, and derive `page` server-side instead of accepting it from the caller.

3. **No CORS policy** — No `cors` middleware is configured. Protection currently relies on 127.0.0.1 binding and browser SOP, not an explicit server policy. Add `cors` middleware configured to allow only the app's own origin.

4. **`frontmanPlugin` phones home to `api.frontman.sh`** — `@frontman-ai/vite ^0.5.2` has access to the source tree and establishes an outbound connection to an external host at dev/build time. Audit what data is transmitted, pin the version, and evaluate whether it should be present in CI.

5. **`vite 7.0.0–7.3.3` high-severity CVEs** — GHSA-fx2h-pf6j-xcff (`server.fs.deny` bypass on Windows) and GHSA-v6wh-96g9-6wx3 (NTLMv2 hash disclosure via UNC path) both have fixes available. Run `npm audit fix` to upgrade to 7.3.4+.

6. **`body-parser` DoS via invalid `limit`** — GHSA-v422-hmwv-36x6 silently disables request-body size enforcement when the `limit` value is invalid, enabling DoS via oversized payloads. Fix available via `npm audit fix`.

7. **Floating minor versions on direct dependencies** — `express: ^4.19.2`, `drizzle-orm: ^0.45.2`, `pino: ^10.3.1`, `leaflet: ^1.9.4` all use `^` ranges. Pin to exact versions to prevent silent upgrades introducing new vulnerabilities.

8. **`WEATHER_API_KEY` visible at debug log level** — `LOG_LEVEL` is unconstrained in `.env.example`. If a developer sets `LOG_LEVEL=debug`, pino-http will log full request objects that may include the API key in outbound request context. Redact the header in pino-http serialiser config, and document the risk in `.env.example`.

<details>
<summary>Details</summary>

### NaN locationId silently queries the database

In `locations.ts`, the delete handler has an explicit guard:

```ts
if (Number.isNaN(locationId)) {
  response.status(422).json({ detail: 'locationId must be a number' });
  return;
}
```

The GET single-location and refresh handlers don't have this check — they pass `Number(request.params.locationId)` straight to `getLocation()` and the weather refresh path. SQLite handles `NaN` as `NULL` in the prepared statement, so these routes always return not-found for non-numeric IDs rather than a validation error. The contract violation is: a caller supplying a malformed ID gets a 404 that looks like a missing resource, not a 422 that correctly signals a bad request.

### Log injection via `/api/logs`

The `event` field is validated with `FRONTEND_EVENT_PATTERN = /^[a-z][a-z0-9_.:-]{1,63}$/` — a tight allowlist. The `metadata` object is accepted with only `typeof metadata === 'object'` and passed directly to `logger.info({ source: 'frontend', event, metadata, ... })`. Any JSON object the caller supplies becomes part of the structured log record. Keys like `level`, `time`, or `service` would collide with pino's own top-level fields depending on how the log aggregator flattens nested objects, and arbitrary content can plant patterns that trigger false-positive security alerts. The `page` field is also taken from `request.body.page` rather than being derived from the `Referer` header or set server-side, so callers can assign it any string.

### Missing CORS configuration

No `cors` import or middleware appears in `server.ts` or `locations.ts`. The current protection is architectural: the server binds to `127.0.0.1`, so cross-origin browser requests can't reach it unless it's proxied. That's not a server-side policy — it's an operational constraint that can change. A reverse proxy, a Vite dev proxy, or a future deployment change that binds to `0.0.0.0` would expose the API without any CORS guardrail. An explicit `cors({ origin: process.env.ALLOWED_ORIGIN })` call in `server.ts` makes the policy independent of the deployment topology.

### `frontmanPlugin` and its dependency chain

`vite.config.ts` configures the plugin with `host: 'api.frontman.sh'` and both `projectRoot` and `sourceRoot` pointing at the frontend directory. The plugin runs during `vite dev` and `vite build`, has read access to the source tree, and makes outbound connections to an external host. The `^0.5.2` version constraint means any `0.5.x` release is accepted silently.

The `npm audit` tree shows that `@frontman-ai/vite` pulls in `puppeteer-core` (which carries `extract-zip` path traversal and `ws` memory exhaustion), `lighthouse` (which adds `@sentry/node` and its OpenTelemetry chain), and several other heavy transitive dependencies. These are build-time tools so they don't run in the production Express process, but they do run in CI and on developer machines. The question to answer before the next deployment: what does the plugin send to `api.frontman.sh`, and should it be excluded from production CI pipelines?

### Dependency vulnerabilities requiring immediate attention

The three findings that are independent of the `frontmanPlugin` chain and have straightforward fixes:

- **`vite` (confirmed)**: GHSA-fx2h-pf6j-xcff — `server.fs.deny` bypass via Windows alternate paths (e.g. short filenames, UNC paths), allowing the dev server to serve files outside the allowed root. GHSA-v6wh-96g9-6wx3 — NTLMv2 hash disclosure when a crafted UNC path is requested. Both affect the dev server on Windows. `npm audit fix` resolves both by upgrading to 7.3.4.
- **`body-parser` (confirmed, via express)**: GHSA-v422-hmwv-36x6 — when the `limit` option receives an invalid value, body-parser silently disables size enforcement instead of erroring. This allows unbounded request bodies to reach route handlers. `npm audit fix` pulls in the patched version via an express upgrade.
- **`@vitest/mocker` (confirmed)**: GHSA-82fw-gwwq-j7x9 — path traversal via redirect mock, affecting `vitest run` and `vitest watch`. Not a production concern, but can be exploited in a CI environment where tests are run against untrusted input. Fix available.
